# SaaS Physics v2 — Economic System architecture (Phase 0 note)

Written before any v2 economics was added, from the frozen v1.3 baseline
(`v1.3-arr-physics`, `44f7652`). This note fixes the ontology and the source-of-truth
hierarchy the four gates build on. Where a gate's implementation departs from it, the
departure is recorded in that gate's Research Note.

## 0. The one decision that shapes everything

**Is ARR a primary stock, or an aggregate derived from lower-level state?**

Both, by layer, and never both at once for the same cohort:

| Layers active | Primary state of a cohort | ARR is |
|---|---|---|
| ARR Physics only (v1.3, the null world of every v2 layer) | MRR balance (`c.live`) | the primary stock, exactly as v1.3 |
| + Customer Physics | customers `n` and MRR balance | still the cohort's stock; **its transition is generated by customer mechanics** (logo survival × survivor economics), so dollar retention is explained, not asserted |
| + Monetization Physics | customers `n` and **per-customer component state** (fixed € + Σ penetration × units × price) | **derived**: cohort MRR = n × per-customer revenue ÷ 12, recomputed every month from the components; never carried separately |

Company ARR is always Σ cohort ARR (the v0.1 cohort spine, unchanged). ARPA is always
ARR ÷ customers, never a stock. Revenue components are always Σ over cohorts of
n × component revenue, never a separate ledger. There is exactly one place each quantity
lives; the others are readouts.

## 1. Object map

```
COMPANY (run)
│  months[]  — the company record: sums of the cohort rows + P&L + cash, one per month
│
├── ACQUISITION                    (v1.2/v1.3, unchanged in v2)
│     law:      N(S&M) linear or bounded; realised through the pending ledger after L months
│     state:    pending entries {spendMonth, matureMonth, sm, newARR, law-at-spend}
│     → cohort at maturity: initialARR, and (Gate A) customers = initialARR ÷ ARR per new logo
│
├── CUSTOMERS                      (Gate A; null = v1.3)
│     cohort state:  n (continuous count), MRR
│     transitions:   logo survival l · contraction c · survivor expansion e   (monthly)
│     flows:         logo-churn ARR, contraction ARR, expansion ARR  → leakage = logo churn + contraction
│     derived:       ARPA = ARR ÷ n per cohort and company; persistence P = L(1 − C) is DERIVED, not input
│
├── MONETIZATION                   (Gate B; null = Gate A; requires Customers on)
│     per-customer state (per cohort): fixed € · components[{penetration, units, price, caps}]
│     transitions:   contraction (uniform survivor shrink) → price growth → usage growth (to a cap) → adoption (to a cap)
│     flows:         price effect, usage effect, adoption effect  (these ARE expansion; the generic e is bypassed)
│     derived:       per-customer revenue; cohort MRR; component mix of ARR; headroom used
│
├── CONTRACT / BILLING + CASH      (Gate C; null = Gate B)
│     policy:        billing term T, timing (advance / arrears), collection delay d
│     state:         deferred revenue (advance) or contract asset (arrears) per cohort; receivables (company)
│     flows:         billings = revenue + Δdeferred; collections = billings shifted by d; cash costs when incurred
│     derived:       cash FCF (≠ EBITA when on); EBITA unchanged
│
└── INTERVENTIONS                  (Gate D; null = no interventions)
      objects:       {target, effect (add | multiply), startMonth, lagMonths, durationMonths, cost}
      resolver:      lawAt(t) — the assumptions in force in month t = base laws + active hypotheses
      flows:         intervention cost (its own P&L line, cash when incurred)
      provenance:    every month records which interventions were active and what they changed
```

## 2. Classification of every new object

| Kind | Objects |
|---|---|
| **Primary state** | cohort customers `n`; cohort MRR (until Monetization is on); per-customer components (Monetization on); pending-acquisition entries; deferred / contract-asset balance per cohort; receivables; cash |
| **Derived state** | company ARR (Σ), ARPA, cohort MRR under Monetization, component mix, deferred total, headroom used, persistence under Customers (= L(1−C)) |
| **Flow** | new ARR, logo churn, contraction, expansion (generic, or price/usage/adoption), revenue, billings, collections, expansion cost, intervention cost, cash FCF |
| **Transition (law)** | logo retention L, contraction C, expansion e; fixed/variable price growth, usage growth, adoption rate, unit/penetration caps; CAC coefficient, capacity; persistence (only while Customers is null) |
| **Policy / assumption** | S&M, R&D, G&A; billing term, timing, collection delay; opening customers; ARR per new logo; interventions (hypotheses, never laws) |
| **Measurement (Layer B, never settable)** | R12M GRR/NRR + its logo / contraction / expansion decomposition, R12M logo retention, ARPA path, monetization mix and price/usage/adoption R12M, cash conversion, coefficient / average / marginal / cohort payback |
| **Optional mechanism** | every v2 layer, each with a null that reproduces the layer below |

## 3. Ownership rules (what may write what)

1. **Retention.** With Customers on, `persistenceAnnual` is not read; the cohort's dollar
   persistence is `l × (1 − c)` from logo survival and contraction. The Change surface shows
   persistence as derived. A user who wants v1.3's 90% persistence sets L and C with
   L(1 − C) = 0.90 (the signature experiment does exactly that).
2. **Expansion.** With Monetization on, `expansionCoefficientAnnual` is not read; survivor
   revenue change comes from price, usage and adoption drivers only. The run reports
   `mechanisms.genericExpansionBypassed = true`. There is never a month in which both create
   growth.
3. **Opening ARR.** With Monetization on, the opening cohort's per-customer components define
   its revenue; `openingARR` becomes derived (= openingCustomers × per-customer revenue) and
   the product shows it as such. One source of truth beats an input that could disagree
   with its own decomposition.
4. **Revenue vs billings vs cash.** `revenue` is recognised as v1.3 does (midpoint MRR);
   `billings = revenue + Δdeferred` by construction; `collections = billings` shifted by the
   collection delay; cash FCF = collections − cash costs. `ebita` is untouched by Cash Physics.
5. **Laws vs hypotheses.** An intervention never becomes a coefficient. It is resolved into
   `lawAt(t)` month by month and stamped on every month record and every pending-acquisition
   entry it touched, so provenance survives.
6. **Bands.** Age-dependent bands (v0.3) remain the v1.3 path's mechanism. Customer Physics
   uses flat customer laws; setting both is rejected at the boundary rather than silently
   combined (recorded as a Gate A boundary).

## 4. Modules

`engine.js` orchestrates one monthly loop and owns every stock. Layer transitions are pure
functions in their own UMD modules, inlined by `build.js` before the engine:

| Module | Owns (pure functions only) |
|---|---|
| `customers.js` | monthly customer transition; per-cohort customer rows; nothing about cash |
| `monetization.js` | per-customer component transition and revenue composition |
| `cash.js` | deferred / contract-asset schedule, billings, collections |
| `interventions.js` | validation and `lawAt(t)` resolution; cost schedule |
| `kpi.js` | measurement (extended, no economics) |
| `integrity.js` + `v2-checks.js` | assertions |

No module keeps state between calls; no module maintains its own ARR, customer count or
cash. The engine passes state in and takes the transition out.

## 5. Null and compatibility

Every layer's null: `logoRetentionAnnual: null`, `monetization: null`,
`billingTermMonths: null` + `collectionDelayMonths: 0`, `interventions: []`. With all at null
the engine must reproduce `baseline-v1.3-full.json.gz` — the complete v1.3 state (all month
fields, all cohorts and rows, R12M and acquisition/expansion measures at every T, summary,
derived, ledger, pending, portfolio capital) for twelve worlds including every v1.3
mechanism on — to €1e-6. That gate (`v2-checks.js` ALL-NULL-V13) is the first check of every
commit in this programme.

## 6. Deliberately not built in v2

Per-customer simulation (customers are continuous cohort counts — no fake precision);
customer-size heterogeneity and concentration (recorded as a Gate A boundary); a general
pricing taxonomy; refunds, breakage, bad debt, payables, tax, debt, capex; causal inference
for interventions; valuation.
